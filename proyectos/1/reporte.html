Objetivos

Quisimos implementar un juego que mostrara una secuencia de celdas en una cuadrícula y que retara al usuario a repetir la secuencia de memoria.

La implementación debía usar técnicas de la clase de programación orientada a objetos y tener ciertas características funcionales. En particular, nos propusimos:

  • usar la librería p5.js
  • generar patrones aleatorios y representarlos gráficamente en la cuadrícula
  • permitir al usuario usar clics del ratón para intentar reproducir el patrón presentado
  • verificar si el intento del usuario fue correcto e indicar si lo fue o no
  • ofrecer al menos tres opciones básicas de dificultad

Se intentó dar una presentación visual atractiva desde el inicio, usando colores y animación. Sin embargo, ese no fue el enfoque principal.

Dadas las instrucciones del primer proyecto, nos limitamos a las funciones de la librería base p5.js, y no usamos addons como p5.quadrille.js.

Decisiones arquitecturales o de diseño técnico

GitLab, Vite y el modo instancia

Para empezar, necesitábamos una forma de almacenar el código y colaborar. Aprovechamos las cuentas de GitLab de cada uno, creadas para acceder a los materiales del curso, para crear un repositorio Git.

Nuestros proyectos, así como este reporte, se albergan en GitLab Pages a través de una página estática generada con Vite. Debido a la naturaleza modular de este modelo de desarrollo, nuestro código usa el modo instancia de p5.js y no el modo global. Por eso, nuestras funciones típicamente tienen un parámetro p que permite acceder a las rutinas de dibujo, como p.background(…) o p.rect(…).

Páginas múltiples

Necesitábamos ofrecer distintos niveles de dificultad. Además, queríamos mostrar una pantalla especial cuando el jugador perdiera. Rápidamente resultó evidente que era necesaria alguna forma de definir varias interfaces posibles, presentarlas según el contexto y transicionar entre ellas.

Para esto, se definió un sistema de páginas. Cada página define funciones para dibujar un fotograma y para reaccionar a interacciones como clics. Un componente, llamado el navegador, se encarga de recibir directamente las llamadas de draw() o mouseClicked() provenientes de p5.js y pasarlas a la página actual. Cada página tiene acceso a una referencia al navegador, y puede usarla para ceder el lienzo a una página nueva: this.navigator.switchPage(p, WelcomePage), por ejemplo.

Opcionalmente, una página puede recibir información de la página anterior. La página que aparece cuando el jugador pierde, por ejemplo, recibe de la página del juego un número que se muestra como su calificación. Esto se logra con expresiones como this.navigator.switchPage(p, GameOverPage, { points: this.level - 1 }).

Se definió una clase abstracta, llamada Page, para expresar en el código la interfaz deseada de una página. Esta clase también ofrece un constructor mínimo por defecto que se comparte entre todas las páginas que creamos.

Dibujo

El lienzo se dibuja en una forma de proceso jerárquico. La página actual tiene un método, draw, que a su vez llama el método draw de sus componentes más pequeños, como una cuadrícula, un botón o una pelota saltarina. Los componentes, a su vez, a menudo llaman el método draw de sus propios componentes anidados; por ejemplo, la cuadrícula llama la función de dibujo de sus celdas.

Las animaciones se implementan de dos formas principales. La primera forma involucra almacenar un estado dentro del objeto animado. Con cada fotograma, este estado se actualiza para progresar la animación. Las pelotas saltarinas, así como los botones, funcionan de esta manera. Este método permite a las animaciones reaccionar en tiempo real a condiciones de interacción. Por ejemplo, los botones inmediatamente retroceden a su color de base cuando el puntero deja de estar sobre ellos; en otras palabras, esa animación es interrumpible.

La segunda involucra almacenar solo un dato: el punto en el tiempo en que empezó la animación. Entonces, se ajusta la apariencia del objeto en función del tiempo transcurrido. Esto es algo más elegante, pero, cuando se usó este método, no hubo interrumpibilidad. La mayoría de las animaciones usaron esta estrategia.

Interactividad

La principal interactividad ocurre con botones y celdas. Los botones permiten seleccionar la dificultad, por ejemplo. Las celdas permiten intentar reproducir una secuencia con el ratón.

Para hacer funcionar a los botones, se usa el método button.intersectsWith(x, y) cuando se recibe un clic para revisar si el clic corresponde a un botón en particular. Por ejemplo, la página de bienvenida usa un bucle para revisar cada uno de los tres botones. El método está implementado con matemáticas simples, aprovechando el conocimiento del botón de sus propias dimensiones y posición.

En cuanto a las celdas, se llama un método de la cuadrícula: grid.intersection(x, y). Se devuelven la fila y columna de la celda correspondiente. La implementación también usa un par de expresiones matemáticas simples.

El diseño del cursor cambia si está encima de un elemento con el que se puede interactuar. Esto se implementa con una revisión rápida mientras se dibuja el fotograma.

Lógica

El juego se divide en cuatro fases:

  • la fase en que se reproduce el patrón
  • la fase en que el usuario debe repetir el patrón
  • la fase entre patrones después de que el usuario haya acabado un patrón
  • la fase después de que el usuario acaba con todas sus vidas

Estas fases se representan internamente y controlan, por ejemplo, si se ignoran los clics o si se muestra un mensaje de retroalimentación (como «¡bien!» o «ups»).

La generación de los patrones es aleatoria. La única condición adicional es que una misma celda no puede aparecer dos veces seguidas.

Para verificar si un patrón introducido por el usuario es correcto, simplemente se comparan las coordenadas una a la vez con el patrón que se generó.

Resultados y limitaciones

El resultado es un juego interactivo que cumple con los objetivos básicos propuestos. Se puede elegir entre tres opciones básicas de dificultad: «Fácil», «Medio» y «Difícil». La dificultad afecta el tamaño de la cuadrícula, la longitud de los patrones y el número de vidas iniciales.

Se usan animaciones ampliamente y hay varios elementos decorativos.

La implementación está profundamente orientada a objetos. Hubo un esfuerzo de diseñar y escribir los sistemas de la forma más limpia posible. El resultado está documentado con comentarios detallados. Sin embargo, con el tiempo, la complejidad se fue incrementando. A futuro, es posible hacer cambios para mejorar la elegancia y simplicidad.

Código muerto

Mientras se estaba escribiendo el programa, se introdujeron funciones que terminaron sin usarse. Por ejemplo, al principio consideramos poner elementos a los lados de la cuadrícula del juego, como texto o botones. Por eso, la implementación de la cuadrícula tiene la habilidad de guardar márgenes a la izquierda y la derecha. Esta habilidad no se usa.

Otro ejemplo es la función async preload() definida en la clase abstracta Page. El objetivo de esa función era permitir la carga de imágenes asincrónicamente, lo cual no puede hacerse correctamente dentro de los setup o draw sincrónicos. Al final, no usamos imágenes.

Para mejorar el proyecto y simplificarlo, estas funciones deberían eliminarse a futuro.

Accesibilidad

La única forma de interacción con el juego es visual. No es posible usar audio, por ejemplo, para recibir el patrón a memorizar o para percibir los elementos de interfaz. En particular, las tecnologías de asistencia no pueden entender el juego porque se dibuja manualmente en un lienzo HTML; no se usan elementos semánticos. En parte, la librería p5.js conduce a este resultado porque está diseñada para proyectos visuales. Sin embargo, también ofrece varias funciones de accesibilidad, y es enteramente posible combinarlas con las capacidades nativas del DOM para ayudar a que más personas puedan cómodamente jugar.

Es posible ajustar el tamaño del texto del juego a través de la interfaz del navegador.

Jugabilidad

Hemos visto que varias personas se divierten con el juego y se sienten motivadas a intentar lograr más niveles.

Actualmente, todos los modos muestran la secuencia de celdas a la misma velocidad. Algunas personas encuentran esa velocidad demasiado rápida al principio. Podríamos mejorar esto haciendo que el patrón se muestre más pausadamente al principio y aumente su velocidad con el tiempo, sobre todo en el modo fácil.

Dentro de un mismo modo de dificultad, todos los niveles son idénticos, y no hay progresión. Esto se podría cambiar para hacer el juego algo más emocionante.

Uso de modelos de lenguaje

En general, no se usaron modelos de lenguaje para escribir porciones significativas del código. Sin embargo, sí se usaron para recordar cómo usar APIs de JavaScript. También se usaron para obtener ideas, explicaciones, e incluso ocasionalmente para ver ejemplos de implementación de funciones o clases.

Este uso varió entre los distintos miembros del equipo.

Visión a futuro

A futuro, nos gustaría que nuestro juego se le notara mucho mas el cambio de dificultad a medida que avanzen los niveles, por ejemplo aumentando la velocidad en que se muestran las cuadriculas. También teniamos planeado mejorar un poco mas la interfaz, con mejores animaciones y agregar un modo multijugador para que las personas pudieran jugar juntas.
