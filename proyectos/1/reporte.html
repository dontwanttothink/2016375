Informe

Este documento corto describe los objetivos del proyecto, las decisiones técnicas que se tomaron mientras se desarrolló, los resultados (incluyendo sus limitaciones) y los materiales referenciados.

Objetivos

Quisimos implementar un juego que mostrara una secuencia de celdas en una cuadrícula y que retara al usuario a repetir la secuencia de memoria.

La implementación debía usar técnicas de la clase de programación orientada a objetos y tener ciertas características funcionales. En particular, nos propusimos:

  • usar la librería p5.js
  • generar patrones aleatorios y representarlos gráficamente en la cuadrícula
  • permitir al usuario usar clics del ratón para intentar reproducir el patrón presentado
  • verificar si el intento del usuario fue correcto e indicar si lo fue o no
  • ofrecer al menos tres opciones básicas de dificultad

Se intentó dar una presentación visual atractiva desde el inicio, usando colores y animación. Sin embargo, ese no fue el enfoque principal.

Dadas las instrucciones del primer proyecto, nos limitamos a las funciones de la librería base p5.js, y no usamos addons como p5.quadrille.js.

Decisiones arquitecturales o de diseño técnico

GitLab, Vite y el modo instancia

Para empezar, necesitábamos una forma de almacenar el código y colaborar. Aprovechamos las cuentas de GitLab de cada uno, creadas para acceder a los materiales del curso, para crear un repositorio Git.

Nuestros proyectos, así como este reporte, se albergan en GitLab Pages a través de una página estática generada con Vite. Debido a la naturaleza modular de este modelo de desarrollo, nuestro código usa el modo instancia de p5.js y no el modo global. Por eso, nuestras funciones típicamente tienen un parámetro p que permite acceder a las rutinas de dibujo, como p.background(…) o p.rect(…).

Páginas múltiples

Necesitábamos ofrecer distintos niveles de dificultad. Además, queríamos mostrar una pantalla especial cuando el jugador perdiera. Rápidamente resultó evidente que era necesaria alguna forma de definir varias interfaces posibles, presentarlas según el contexto y transicionar entre ellas.

Para esto, se definió un sistema de páginas. Cada página define funciones para dibujar un fotograma y para reaccionar a interacciones como clics. Un componente, llamado el navegador, se encarga de recibir directamente las llamadas de draw() o mouseClicked() provenientes de p5.js y pasarlas a la página actual. Cada página tiene acceso a una referencia al navegador, y puede usarla para ceder el lienzo a una página nueva: this.navigator.switchPage(p, WelcomePage), por ejemplo.

Opcionalmente, una página puede recibir información de la página anterior. La página que aparece cuando pierdes, por ejemplo, recibe de la página del juego un número que se muestra como tu calificación. Esto se logra con expresiones como this.navigator.switchPage(p, GameOverPage, { points: this.level - 1 }).

Se definió una clase abstracta, llamada Page, para expresar en el código la interfaz deseada de una página. Esta clase también ofrece un constructor mínimo por defecto que se comparte entre todas las páginas que creamos.

Dibujo

El lienzo se dibuja en una clase de proceso jerárquico. La página actual tiene un método, draw, que a su vez llama el método draw de sus componentes más pequeños, como una cuadrícula, un botón o una pelota saltarina. Los componentes, a su vez, a menudo llaman el método draw de sus propios componentes anidados; por ejemplo, la cuadrícula llama la función de dibujo de sus celdas.

Las animaciones se implementan de dos formas principales. La primera forma involucra almacenar un estado dentro del objeto animado. Cada fotograma, este estado se actualiza para progresar la animación. Las pelotas saltarinas, así como los botones, funcionan de esta manera. Este método permite a las animaciones reaccionar en tiempo real a condiciones de interacción. Por ejemplo, los botones inmediatamente retroceden a su color de base cuando el puntero deja de estar sobre ellos; en otras palabras, esa animación es interrumpible.

La segunda involucra almacenar solo un dato: el punto en el tiempo en que empezó la animación. Entonces, se ajusta la apariencia del objeto en función del tiempo transcurrido. Esto es algo más elegante, pero, cuando se usó este método, no hubo interrumpibilidad. La mayoría de las animaciones usaron esta estrategia.

Interactividad

La principal interactividad ocurre con botones y celdas. Los botones permiten seleccionar la dificultad, por ejemplo. Las celdas permiten intentar reproducir una secuencia con el ratón.

Para hacer funcionar a los botones, se usa el método button.intersectsWith(x, y) cuando se recibe un clic para revisar si el clic corresponde a un botón en particular. Por ejemplo, la página de bienvenida usa un bucle para revisar cada uno de los tres botones. El método está implementado con matemáticas simples, aprovechando el conocimiento del botón de sus propias dimensiones y posición.

En cuanto a las celdas, se llama un método de la cuadrícula: grid.intersection(x, y). Se devuelve la fila y columna de la celda correspondiente. La implementación también usa un par de expresiones matemáticas simples.

El diseño del cursor cambia si está encima de un elemento con el que se puede interactuar. Esto se implementa con una revisión rápida mientras se dibuja el fotograma.

Lógica

El juego se divide en cuatro fases:

  • la fase en que se reproduce el patrón
  • la fase en que el usuario debe repetir el patrón
  • la fase entre patrones después de que el usuario haya acabado un patrón
  • la fase después de que el usuario acaba con todas sus vidas

Estas fases se representan internamente y controlan, por ejemplo, si se ignoran los clics o si se muestra un mensaje de retroalimentación (como «¡bien!» o «ups»).

La generación de los patrones es aleatoria. La única condición adicional es que una misma celda no puede aparecer dos veces seguidas.

Para verificar si un patrón introducido por el usuario es correcto, simplemente se comparan las coordenadas una a la vez con el patrón que se generó.
